# Паперны для максимально эффективного использования LLM

В данной главе рассматриваются несколько техник, которые помогут достичь большей автономности, а при том же уровне автономности - повысить надежность:

**Потоковый/промежуточный вывод**  
Более высокая задержка не становится проблемой, если в процессе есть какой-то прогресс или промежуточный вывод.

**Структурированный вывод**  
Требование к LLM выдавать результат в заранее определенном формате увеличивает вероятность того, что он будет соответствовать ожиданиям.

**Человек в цикле**  
Архитектуры с высокой автономностью выигрывают от вмешательства человека во время их работы: прерывания, одобрения, развилки или отмены.

**Режимы двойного сообщения**  
Чем дольше LLM отвечает, тем вероятнее, что пользователь отправит новый запрос, прежде чем предыдущий будет обработан.

<br/>

$ node ./a-structured-output.js

### Потоковая передача вывода LLM по токенам

:warning: Походу код есть только в книге. Надо будет когда-нибудь добавить (никогда).

Иногда требуется получать потоковый вывод от каждого вызова LLM внутри более крупного приложения, что полезно, например, при создании интерактивного чат­ бота, где вы хотите отображать каждое слово сразу после того, как оно сгенериро­вано LLМ.

<br/>

```js
const input = {
  messages: [
    new HumanMessage(`Какой временной промежуток разделяет открытие иероглифов майя и их успешную расшифровку Юрием Кнорозовым?`)
  ]
}

const output = await agent.streamEvents(input, {version: "v2"});

for await (const { event, data } of output) {
  if (event === "on_chat_model_stream") {
    const msg = data.chunk as AIMessageChunk;
    if (msg.content) {
      console.log(msg.content);
    }
  }
}
```

### Режим "Человек в цикле" (Human in the Loop, HITL)

Смысл - разработчик или конечный пользователь может влиять на то, что делает LLM.

Каждый раз, когда вызывается граф, он сначала использует *модуль контрольных точек* (`checkpointer`), чтобы получить последнее сохраненное состояние — если оно есть, — и объединяет новый ввод с предыдущим состоянием. И только затем выполняются первые узлы. Это ключевой момент для реализации режимов участия человека в процессе, т. к. все они опираются на то, что граф "помнит" предыдущее состояние.

**Первый режим — прерывание (`interrupt`)** — это самая простая форма управления: пользователь наблюдает за потоковым выводом приложения в реальном времени и вручную прерывает его, когда сочтет нужным. Сохраняется состояние на момент последнего завершенного шага до того, как пользователь нажал кнопку прерывания. После этого пользователь может выбрать:

- Продолжить выполнение с этого места, и вычисления продолжатся так, как будто они не были прерваны (см. *раздел "Продолжение выполнения"* далее).
- Отправить новый ввод в приложение (например, новое сообщение в чат-боте), что отменит все запланированные шаги и начнет обработку нового ввода (см. *раздел "Перезапуск"* далее).
- Ничего не делать, и тогда выполнение просто не продолжится.

<br/>

```shell
$ node ./c-interrupt.js 

[Остановлено: превышен лимит времени]
```

<br/>

Второй режим управления — `authorize` — позволяет пользователю заранее обозначить, что управление должно передаваться ему каждый раз перед вызовом определенного узла. Такой подход обычно используется для подтверждения действий инструмента: перед тем как приложение вызовет какой-либо инструмент (или конкретные инструменты), выполнение приостанавливается и запрашивается подтверждение. В этот момент у вас есть несколько вариантов:

- продолжить выполнение, разрешив вызов инструмента;
- отправить новое сообщение, чтобы направить бота в другое русло — в этом случае вызов инструмента не произойдет;
- не предпринимать никаких действий.
